# ADR-0037: Compare at scale — one-to-many and many-to-many batch redlining, in the standalone target, with confirmable pairing

- **Status:** Accepted  <!-- approved 2026-09-10 in a planning conversation; the scope register rows (16, 17) and the feature spec land in the same change. -->
- **Date:** 2026-09-10
- **Extends (does not supersede):** **ADR-0008** (Compare categorises, never suppresses — extended to cover *pairing*), **ADR-0022** (standalone host-portable target — this is where these features live), **ADR-0003** (client-side OOXML loop and its two-documents-in-memory ceiling — the reason these features are *not* in the add-in), **ADR-0017** (PDF comparison — its unmeasured Phase-E gate is why cross-format comparison stays out), **ADR-0001** (no backend — untouched).

## Context

Compare today is strictly **one document against one document**, run **one comparison at a time**. That matches how a lawyer reconciles a single returned draft, and it is how features 08 (Word-vs-Word), 10 (Text/PDF) and their export surfaces (ADR-0020, ADR-0024) were built.

It does not match two workflows that are routine in SG/UK transactional practice:

1. **One-to-many (1:N).** A firm has a **house precedent or an agreed template** and needs to know how each of *N* executed or returned versions departs from it: a standard NDA against the forty variants a client has actually signed; an LMA-based facility agreement against each borrower's negotiated version; a template SPA against every version a counterparty returned during a bidding round. Today this is *N* manual Compare runs, each of which re-uploads and re-preprocesses the template.
2. **Many-to-many (M:N).** Two **deal bundles** — a signing set against a closing set, a data-room folder against the version the counterparty says is current. The documents correspond to each other, but the correspondence is neither given nor reliably recoverable from filenames: `Project_Falcon_SPA_v7_exec.docx` in one folder is the counterpart of `SPA (clean) 2026-08-30.docx` in the other, and the disclosure letter, the side letter and the SPA all share the same defined terms and the same cast of parties.

Both are, today, either done by hand or done by uploading a whole deal bundle to a cloud comparison service — precisely the confidentiality problem this product exists to remove.

Four constraints shape the decision.

- **The add-in cannot host this.** ADR-0003 records the `getFileAsync` **two-documents-in-memory** ceiling, and `spec/ARCHITECTURE.md` → Performance Guidelines makes it a design rule ("serialise OOXML reads; for a second compare document use File-API upload"). Holding a template plus a queue of *N* variants inside the Word task pane is structurally wrong, not merely slow.
- **Mis-pairing is the pairing analogue of suppression.** ADR-0008's rule is that no change may be hidden. A *silently wrong* pairing in the M:N case is worse than a hidden change: comparing the SPA against the disclosure letter produces a plausible-looking, fully-populated, whole-document rewrite that a reader has no cue to distrust. The output looks like a redline; it is noise.
- **Memory is the first thing that breaks.** Each `PipelineResult` holds two `ParaRecord[]`, and every `ParaRecord` carries the paragraph's `rawXml` — so a result is roughly document-sized on both sides. Retaining *N* of them is not a tuning problem, it is an out-of-memory crash at a value of *N* the workflows above reach routinely.
- **Compare runs on the main thread today** (chunked yields, `WORD_DIFF_CHUNK = 25`). That is adequate for one pair and inadequate for a hundred.

## Decision

Bring **one-to-many** and **many-to-many** comparison into scope as two features sharing one spec (`spec/features/17-compare-batch.md`; the scope register rows **16** and **17**), built on the shipped Compare pipeline, subject to the following nine decisions.

1. **The output of one-to-many is *N* separate redlines** — the **editable tracked-changes `.docx`** a single Compare run produces today, once per variant, plus a compact index of the batch. (Amended 2026-09-10, before the feature closed: this clause originally also promised the read-only rendered snapshot per pair. It is not batched — see Consequences and spec §2.2 for the reasoning. Corrected here rather than only qualified there, because Decision is the binding clause.) **The aggregate "deviation matrix" is explicitly NOT in this scope** and is deferred to a separate desktop product. (Maintainer decision, 2026-09-10.)

2. **Both features land in the standalone/web target only** (`src/web/**`, `src/host-web/**`). **The Word add-in is untouched** — no new tab, no new panel, no behaviour change. ADR-0003's two-document ceiling is the reason, and it is a structural reason, not a performance one.

3. **Pairing for many-to-many is proposed and user-confirmable, never silent.** The system computes a proposed assignment, renders a **pairing grid** showing every proposed pair, its score, and its top rivals, and runs **nothing** until the user confirms. Three confidence bands drive presentation only — **auto-pair** (proposed, pre-ticked), **propose-with-rivals** (proposed, showing the top two alternatives), **unmatched** (added or removed document, shown as such). No band ever suppresses a candidate from view. This is ADR-0008 applied to pairing.

4. **Pairing signals are lexical and structural, never semantic.** In priority order: **content similarity** (MinHash / Jaccard over the paragraph hashes the preprocess pass already computes), then **filename similarity** after stripping version tokens, then — **as a tie-breaker only** — defined-term and party-cast overlap. The third signal is explicitly weak: inside one deal bundle the SPA, the disclosure letter and the side letter share the same cast and most defined terms, so it does not discriminate and must never dominate.

5. **Assignment is a global optimum, not a greedy walk.** Build a cost matrix and solve it with the **Hungarian algorithm**, padded with dummy rows and columns priced at a **no-match cost**, so added and removed documents fall out of the assignment naturally rather than being force-matched to their least-bad rival. *N*, *M* ≤ ~50, so the O(n³) cost is irrelevant here. *Amended 2026-09-11, before the feature was closed:* the dummy price is **derived, not chosen** — `(1 − noMatchScore) / 2`, because leaving a real A and a real B both unmatched pays it twice. The spec's original `1 − noMatchScore` would have doubled the effective threshold and paired documents sharing almost nothing (spec §6.4).

   *Amended again 2026-09-11, before the feature was closed:* the solve runs in **two phases**. Phase 1 admits only cells the **content** corroborates; a cell with no content evidence is priced strictly above the cost of leaving both its documents unmatched, so it cannot displace a content-supported pair. Phase 2 then runs over phase 1's leftovers, on the filename alone, and only over cells where the content signal was *unavailable* rather than merely weak. This replaces the attempt to make one score do both jobs — see Decision 6 for why that could not work (spec §6.4).

6. **Cross-format *comparison* is out of scope.** Pairing *may* be designed to accommodate a mixed bundle (a `.docx` on one side, a `.pdf` on the other), but **Word-vs-PDF comparison is not built here**: ADR-0017 Phase E was deferred earlier and its alignment gate was **never measured**. A cross-format pair is surfaced as *unrunnable, pair identified* — never silently skipped, never best-effort compared.

   *Amended 2026-09-11, before the feature was closed:* surfacing such a pair requires it to be *scored*, and a document with no paragraph hashes scores 0 on the dominant signal — which is a statement of dissimilarity rather than of ignorance, and caps every mixed pair below the no-match price. Absent evidence is therefore scored on the filename alone, **capped just above the no-match price** (spec §6.3). A first attempt renormalised outright and produced the opposite failure: a perfectly-named PDF outscored every content-verified pair and displaced a genuine `.docx` counterpart. Filename-only evidence must be enough to beat *nothing* and never enough to beat *something*.

   *Amended again 2026-09-11, before the feature was closed:* the cap alone cannot deliver both halves of that sentence, and a second review caught the spec claiming it did. One number on one scale is either high enough to beat a dummy — in which case it displaces real pairs — or low enough not to, in which case no cross-format pair forms at all: under the cap, this ADR's own motivating example (a `.docx` against the same agreement's `.pdf`, Dice 0.261) stopped pairing and both sides were labelled "no counterpart", which is untrue and leaves the cross-format pair unsurfaced by the opposite route. The cap is therefore retained for what a score *can* do — **ordering** rivals and setting the auto-pair margin, so an uncapped PDF rival cannot suppress a good `.docx` pair merely by existing — while **formation** is answered structurally by the two-phase assignment in Decision 5.

   A pair whose two sides **agree** on a format this build does not batch (PDF against PDF) is a third case, and is reported as such rather than as "cross-format" — two PDFs are not a mismatch, and a reason that is untrue sends the reader looking for one that does not exist.

7. **The template side is preprocessed once and reused across all *N*.** The seam already exists: `runComparePipeline()` takes already-built `ParaRecord[]` and already supports `onProgress` and `abortSignal`. The per-file entry point that re-preprocesses both sides is not the batch entry point.

8. **Execution moves off the main thread into a bounded worker pool**, following the pattern already shipped in `src/shared/render-core/worker/**`. The pool is bounded by `navigator.hardwareConcurrency`. This is a correctness requirement at *N* = 100, not an optimisation.

9. **Results are streamed, never accumulated.** Variants are ingested one file at a time; each run retains only a **compact row** (identity, counts by classification bucket, the artefact handles) and releases its `PipelineResult`. Drill-down into one pair **re-runs that single pair**. The input caps in `io/pdf/limits.ts` are per-run today and gain a per-batch counterpart.

**Prerequisite (blocks all of the above).** `src/features/compare/driver.ts` holds its state in **module-level Preact signals** — a hard singleton that permits exactly one run at a time. It must become **instantiable** before any batch work is possible. This refactor is behaviour-neutral for the existing single-pair panels and is task 1 of the execution plan.

**Out, permanently or by deferral, and named so nobody re-derives them:** no AI or model inference anywhere in pairing or comparison (ADR-0008); no network call of any kind (ADR-0001); no Electron (ADR-0022); no chat or conversational surface; no aggregate deviation matrix (deferred to a separate product); no cross-format comparison (ADR-0017 Phase E remains deferred and unmeasured).

## Rationale

- ***N* separate redlines, not a matrix,** because a redline is the artefact a lawyer already knows how to read, review, and send on. A deviation matrix is a genuinely different product — portfolio analytics with its own UI, its own persistence, and its own performance envelope — and folding it in here would turn a bounded feature into an open-ended one. Owner decision; recorded so it is not re-litigated.
- **The standalone target, because the ceiling is architectural.** The add-in's two-document limit is not a number to be tuned around; it is the shape of `getFileAsync`. The web target already ingests arbitrary files from disk (`host-web/ooxml-loader.ts`), already runs Compare host-free, and already exports rather than mutates. Batch work fits it by construction and fits the add-in not at all.
- **Confirmable pairing, because the failure is invisible.** A wrong pairing does not fail loudly; it produces a complete, well-formed, entirely worthless redline. The only defence is that a human sees the proposed correspondence — with its rivals and its scores — before a single comparison runs. This is exactly why ADR-0008 exists, applied one level up.
- **MinHash/Jaccard over the existing hashes, because the work is already done.** `preprocess/hash.ts` (`fnv1a`, 32-bit) computes a hash per paragraph during preprocessing regardless. Shingling those hashes is close to free, needs no new dependency, is deterministic and auditable, and — unlike any embedding-based approach — is explainable to the user in the pairing grid.
- **Hungarian over greedy, because greedy is order-dependent.** A nearest-neighbour walk over a bundle of near-identical documents gives different answers for different input orders, which is indefensible in a tool whose output a lawyer relies on. At *N* ≤ 50 the globally-optimal solve costs nothing.
- **Streaming, because *N* results do not fit.** This is arithmetic, not caution: two document-sized `ParaRecord[]` per result, times *N*.

## Rejected alternatives

- **An aggregate "deviation matrix" / portfolio dashboard as part of this scope.** Rejected by maintainer decision (2026-09-10): it is a separate desktop product with a different shape. *N* redlines plus a compact index is the deliverable here.
- **Building batch compare in the Word add-in.** Rejected: ADR-0003's two-documents-in-memory ceiling makes an *N*-way queue inside the task pane structurally wrong. No amount of chunking fixes the shape of `getFileAsync`.
- **Silent / fully automatic pairing (highest score wins, run immediately).** Rejected: a mis-pairing produces a plausible whole-document rewrite with no cue that it is wrong — the pairing analogue of suppressing a change, forbidden by ADR-0008.
- **A confidence threshold that drops low-scoring candidates from the pairing grid.** Rejected for the same reason ADR-0008 rejects a default-on "hide low-confidence differences" filter: confidence is a **badge**, never a hidden filter. Every candidate stays reachable.
- **Greedy nearest-neighbour assignment.** Rejected: not globally optimal and order-dependent across a bundle of similar documents; the Hungarian solve is free at this scale.
- **Embedding / model-based document similarity for pairing.** Rejected: needs either a network call (ADR-0001) or a shipped model, and replaces an auditable lexical score with an opaque one. ADR-0008's no-ML stance covers judgement about documents, not only about changes.
- **Defined-term or party-cast overlap as the primary pairing signal.** Rejected on the evidence: within one deal bundle these are near-identical across every document, so they carry almost no discriminating power. Tie-breaker only.
- **Retaining all *N* `PipelineResult`s so drill-down is instant.** Rejected: out-of-memory at realistic *N*. Re-running one pair on demand is fast and bounded.
- **Keeping batch execution on the main thread with the existing chunked-yield model.** Rejected: adequate for one pair, not for a hundred. The worker pool is a correctness requirement.
- **Building cross-format (Word-vs-PDF) comparison to make mixed bundles work.** Rejected here: ADR-0017 gated Phase E on a measured alignment bar that was never measured. Reviving it inside a batch feature would ship an ungated capability by the back door. Mixed pairs are *identified and reported unrunnable*.
- **Making `driver.ts` re-entrant by resetting the module-level signals between runs.** Rejected: it leaves a singleton with a manual discipline attached, and one concurrent run corrupts another's state silently. Instantiation is the fix.

## Consequences

- the scope register gains rows **16** (one-to-many) and **17** (many-to-many); `spec/features/17-compare-batch.md` specifies both; the project's status map is updated in the same change.
- **`compare/driver.ts` stops being a singleton.** This is a prerequisite refactor that touches the existing single-pair Compare panels. It must be behaviour-neutral and is covered by the existing Compare tests plus new ones asserting two concurrent instances do not share state.
- A **second worker pool** joins the codebase alongside RenderCore's worker transport, following the same protocol shape. Pool bounding and cancellation semantics are specified in the feature spec.
- **Input caps become a batch concern.** Today the only caps in Compare are `compare/io/pdf/limits.ts` (PDF, per run) and `MAX_TEXT_PASTE_CHARS` (paste); **the `.docx` path has no size cap at all**, which is survivable at one pair and is not at *N*. A batch `limits.ts` follows the established convention — named constant, typed error, guard that fails *before* any partial work — and a batch that would exceed a cap is refused with the limit named, never silently truncated.
- **All four invariants hold unchanged.** Confidentiality: everything remains client-side, and the existing no-`fetch` invariant lint covers the new code by construction. Jurisdiction: the batch layer adds no locale logic; the classifier and `CompareConfig` are reused verbatim. Scope: this ADR plus the scope register rows *is* the gate. Categorise-never-suppress: extended to pairing, not weakened.
- The add-in's behaviour, tests, and bundle are **unaffected**; the batch surfaces live in the web target only. (They are statically imported by `src/web/WebApp.tsx` rather than lazily code-split — the add-in bundle is untouched either way, and the web shell is a small `useState` over its views, not a router. Code-splitting them is a build-size question to revisit if the web bundle grows, not a correctness one.)
- **A batch produces the editable redline only.** A single Compare run produces the editable tracked-changes `.docx` *and* a read-only RenderCore rendered snapshot (ADR-0020, ADR-0024). Batching the second would cost a full layout pass per pair on top of the comparison, and retaining a hundred rendered snapshots reopens the memory ceiling this ADR's artefact policy exists to close. The snapshot's value is in reading *one* redline, which is what the drill-down is for, so it stays a one-pair artefact and batching it is deferred (spec §2.2, §10). Amended 2026-09-10, before the feature was closed.
- **Config keys must be consumed, not merely resolved.** *Recorded 2026-09-11.* The `compare.batch.pairing.*` keys were resolved correctly by the config layer and then ignored by every module that needed them, so a profile setting them changed nothing — and the resolver's own test passed either way, because it only ever asked the resolver about itself. The settings are now threaded through the pairing functions, and an import wall enforced by a test keeps the tunable constants inside the module that owns the defaults. Generalisable beyond this feature: a config key is not wired until something *downstream of the resolver* can be shown to change when it does.

- **A cap demotes its own pair; it does not end a confirmed run.** *Recorded 2026-09-11.* The per-document byte cap is a pre-flight refusal when a batch is *started*, and must not be one when a confirmed many-to-many run meets a pair the grid already showed with that cap named. The user confirmed knowing that pair would not be compared; throwing at that point loses every other pair's redline to a limitation they had already accepted. Aggregate caps stay whole-batch refusals — they are about what the run would hold at once.

- **The artefact ceiling degrades; it never loses a result.** Past the cumulative retained-artefact limit a row keeps no `Blob`, but its redline is still obtainable by re-running that one pair — on a single download, and lazily one at a time as a "download all" archive is written. `artefactOnDemand` means *not retained*, never *not available*. A ceiling past which a hundred redlines simply could not be got would be a silent loss of results, which is the batch-scale shape of what ADR-0008 forbids.

- **A signal used for two jobs will fail one of them.** *Recorded 2026-09-11.* The filename-only score was asked both to *order* candidates and to decide whether a pair *forms* at all, and no single number could do both: pitched high enough to beat the no-match dummy it displaced content-verified pairs, pitched low enough not to it formed no cross-format pair at all. Two review passes each caught one half. The fix was to stop scaling and separate the questions — a phased assignment answers formation, the score answers ordering. Generalisable: when a tunable has to be moved in opposite directions to satisfy two requirements, the requirements need different mechanisms, not a better constant.

- **The trade the two phases keep is documented, not hidden.** *Recorded 2026-09-11.* A pair that phase 1 *rejected* on content can be picked up in phase 2 by a better-named no-content candidate. That is the intended reading — phase 1 has already said those two documents are not counterparts — but it is a real behavioural consequence and it is pinned by a test rather than left for a future reader to discover.

- **A run consumes the pairing it was given.** *Recorded 2026-09-11.* Confirmation is not a moment, it is a state the run holds: while comparisons are in flight the pairing is not editable, and the way out of a run is to cancel it. Without that, "change the pairing" stayed live for the whole batch, and taking it left finished rows and a written index describing a pairing the grid above them no longer showed — a complete, downloadable redline under a grid saying that pair did not exist. The guard belongs in the driver as well as the button, for the same reason the confirmation gate does.

- **One bad document must not empty the grid, either.** *Recorded 2026-09-11.* Spec §8 case 2 was written for the RUN — a corrupt file fails its own row and the batch continues — and the many-to-many INGEST did not honour it: one `try` around the whole sketch loop turned a single unreadable file into a null proposal, losing every other document in both bundles. An unreadable document now gets a sketch carrying its name and a reason, is kept out of the assignment, and appears as its own row. The general rule: wherever a batch touches N documents, the failure boundary is one document.

- **A derived signal is only as honest as the state it derives from.** *Recorded 2026-09-11.* `running` was derived from `status` precisely so the grid and the runner could not disagree — and then four editing paths reset `status` to `'idle'` mid-run, which made the derived signal say false while a run was still writing rows, disarmed the runner's own re-entry guard, and allowed two concurrent runs into one row list. Deriving state removes the risk of two values drifting apart; it does not remove the need to guard every writer of the value they are derived from.

- **A guard is only as good as the composition it is tested in.** *Recorded 2026-09-11.* The rule that the cast may not decide a band was fixed once and tested once, and the test called the function on a list the production call site would have sliced first — so the fix held for two rivals and failed for three. The remedy was to change the signature until the bug could not be expressed: the function now takes the best rival's score as a number, and a number cannot be sliced. Where a test cannot be given the real composition, change the interface until the wrong composition does not typecheck.

- **A slowdown and a crash are not a trade-off.** *Recorded 2026-09-11.* Spec §6.7 promised that no document in a many-to-many run is preprocessed twice, and delivered it by having each pairing sketch retain its document's `ParaRecord[]` — a hundred of them live at once at the §4.4 caps, which is the shape this ADR's own Context calls "not a tuning problem, it is an out-of-memory crash". The two clauses were in direct contradiction and the spec recorded neither side of it. Resolved in favour of §4.3: sketches keep hashes, and a pair's records are built by the lane that runs it. Where an optimisation and a memory bound disagree, the bound wins, and the spec says which one it gave up.

- **A control that can be used and cannot work is worse than no control.** *Recorded 2026-09-11.* The re-point dropdown offered every side-B document, including ones the assignment can never pair — and choosing one destroyed a correct pairing in silence, because the proposal was rebuilt before the choice was found to be unusable. Offering an option implies it will be honoured; where it will not be, the option must not appear, and the API behind it must refuse as well.

- **A second surface for the same data will drift, and it will drift on the parts nobody re-reads.** *Recorded 2026-09-11.* The many-to-many panel hand-rolled its own copy of the batch row line instead of reusing the one-to-many one, and lost the classification chips, the cancellation notice and the flatten statement — three separate spec clauses, none of them decided against, all of them simply absent. Two reviews found this shape in this feature (the drill-down block, then the row list). Where two surfaces render the same model, the renderer is a component, not a convention.

- **A re-run must reproduce its row, so it reads the run's settings and not the live ones.** *Recorded 2026-09-11.* The one-to-many driver captured config, date and flatten when a batch started, and said in a comment why. The many-to-many driver captured two of the three and left the flatten policy — the only one with a public setter — being read live, so a drill-down or an on-demand redline could be produced under a policy the index denies. When a pattern exists because of a named failure, the second implementation of it needs the whole pattern, not the parts that were convenient.

- **A gate guards a capability, not a method.** *Recorded 2026-09-11.* `runConfirmed()` refused an unconfirmed pairing, and the plan recorded that as the gate being "enforced in the driver". It was enforced in one method. `openPair()` also starts a comparison, checked only whether the pair was runnable, and would hand back a complete change list for a pairing nobody had read. When a rule says *nothing* may happen before a step, the guard belongs at the thing that happens — here the single function that runs a pipeline — not at each entry point someone remembers to add it to.

- **A failure boundary covers everything done to the thing it is drawn around.** *Recorded 2026-09-11.* The per-document `catch` in the many-to-many ingest was drawn around the parse and not the read, so a file that had moved since the picker ran still emptied the whole grid — the same failure this ADR already recorded as fixed, reached through the other half of the same operation. Drawing a boundary at one document means every step that touches that document, not the step the last failure happened to come from.
